AI 에이전트 지식수집 과제 회고 — 왜 순차 구조로는 한계가 있었나

카카오톡 1:1 인터뷰로 흩어진 지식을 모아 고객응대 AI 에이전트를 만드는 온라인 예선 과제를 마치고, 진행 과정에서 반복된 병목을 분석해 더 나은 구조로 다시 설계해본 회고입니다.

이 페이지의 범위 — 과제 수행은 실제로 끝까지 제출을 완료한 작업이고, 구조 재설계는 과제를 마친 뒤 "다시 한다면 이렇게 했을 것"이라는 가정 아래 직접 다시 그려본 개념 설계입니다. 과제의 결과물·제출 자료·대회 측 제공 자료(토큰, API 응답, 심사 기준 등)는 외부 공개 대상이 아니라 이 글에 담지 않았습니다.

1과제 — 흩어진 지식을 모아 판단 경계를 가진 에이전트 만들기

농수산물 직판몰을 가정한 온라인 예선 과제였습니다. 운영 인력 3명, 위탁 생산·배송 담당자 여러 명이 각자 다른 조각의 정보를 들고 있는 상황에서, 카카오톡 1:1 대화로 담당자를 한 명씩 인터뷰해 정보를 모으고, 그 정보로 고객 문의에 응답하는 에이전트를 설계해 카카오 i 오픈빌더로 구현·제출하는 과제였습니다.

문제의 핵심은 지식이 없는 게 아니라, 공식 규정·현장 관행·추측성 답변이 구분 없이 섞여 있다는 점이었습니다. 그래서 설계 원칙을 "모르는 것을 아는 것처럼 답하지 않는다"로 세우고, 담당자 인터뷰 중 확보한 에스컬레이션 절차서(담당자 이관 체계)를 에이전트의 판단 로직으로 그대로 가져와, 애매한 경우 사람에게 넘기는 구조로 구현해 제출을 완료했습니다.

2지식은 어디서 왔는가 — 메신저로 한 명씩 캐낸 과정

판정 로직 안의 모든 규칙은 실제로 존재하는 자료가 아니라, 카카오톡 1:1 채널로 담당자를 한 명씩 인터뷰해서 캐낸 답변에서 나왔습니다. 공식 문서가 있는 경우도 있었지만, 문서에 없는 현장 기준(예외적으로 처리하는 관행, 경계가 애매한 사례)은 전부 이 대화에서 나왔습니다.

3직접 눌러보는 판정 로직

아래는 실제로 설계했던 에이전트의 "레인 판정" 로직을 그대로 코드로 옮긴 데모입니다. 질문 유형을 고르면 실제 판정 순서(절대원칙 검사 → 손해배상 여부 → 대외공개·안전 여부 → 권한 내 처리 가능 여부)를 따라가며 어느 단계에서 어떤 이유로 직접 처리되거나 이관되는지 보여줍니다.

실제 봇에 쓴 시스템 프롬프트의 판정 규칙을 그대로 옮긴 것이며, 외부 AI API를 호출하지 않는 순수 규칙 기반 시뮬레이션입니다. 대회 시나리오의 구체적인 상호명·인명·수치는 포함하지 않았습니다.

4진행 중 반복된 병목 — 전부 한 줄로 처리한 구조

끝내고 돌아보니, 실제 작업 로그에 병목 지점이 뚜렷하게 남아 있었습니다. 관계자 인터뷰 추적, 규정 문서 분석, 지식베이스 정리, 봇 구현까지 네 가지 성격이 다른 작업을 전부 하나의 순차 흐름으로 처리했습니다.

[관계자 인터뷰 추적] → [문서 분석(이미지·PDF)] → [지식베이스 정리] → [봇 구현] 한 명이 한 번에 하나씩, 앞 단계가 끝나야 다음 단계로 이동
  • 연쇄 추적의 병목 — 관계자 10명 중 2명의 연락처를 몰라 "한 명에게 물어보고 모르면 다음 사람에게, 그 사람도 모르면 또 다른 사람에게 재확인"하는 식으로 한 명씩 순서대로 물어야 했습니다. 이 추적에만 반복적으로 시간이 들어갔고, 결국 시간 부족으로 2명은 끝내 확보하지 못한 채 "8/10명이면 충분하다"는 판단으로 넘어갔습니다.
  • 질문 설계와 문서 분석이 서로를 기다림 — 권한위임표(이미지 5장), 에스컬레이션 절차서(PDF), 규정집(HTML) 같은 자료를 분석해야 다음 인터뷰 질문을 구체적으로 설계할 수 있었는데, 두 작업이 한 사람의 시간 안에서 순서를 다퉈야 했습니다. 실제로 "문서 분석을 빠르게 끝내고 봇 구현에 집중해야 한다"는 메모를 남기며 둘 중 하나를 포기하는 식으로 시간을 쪼갰습니다.
  • 마감 압박이 늦게 드러남 — "남은 시간 40분" 같은 메모가 작업 후반에야 등장합니다. 네 작업이 하나의 흐름에 묶여 있어서, 초반에 인터뷰 추적에 쓴 시간이 봇 구현 시간을 얼마나 깎아먹고 있는지 중간에 드러나지 않았습니다.

5연동 과정에서 배운 것 — 지식과 시스템은 서로 다른 레이어다

지식베이스를 다 모은 다음에도, 그걸 실제로 작동하는 봇으로 연결하는 과정에서 배운 점이 따로 있었습니다. 제공된 액션 API(기능 호출용 API 명세)를 분석하면서 "사람에게 물어서 끝내 못 얻은 답을, 시스템 구조를 뒤져서 역으로 찾아낸" 경험이 가장 인상적이었습니다.

  • 사람이 모른다고 답한 것을 데이터 구조에서 확인했다. 인터뷰로는 "이 식별자가 저 식별자로 연결되는지" 아무도 확답하지 못했습니다. 그런데 API의 데이터 모델(스키마)을 하나씩 대조해보니, 한쪽 데이터에는 그 연결 키가 없고 다른 쪽 데이터에는 있다는 게 확인됐습니다. 담당자의 기억이나 구술보다 실제로 시스템에 저장된 데이터 구조가 더 정확한 답을 줄 때가 있다는 걸 체감했습니다. 다음에는 사람에게 묻기 전에 "이 정보가 시스템 어딘가에 이미 구조화되어 있을 가능성"을 먼저 확인하는 순서로 바꿀 것 같습니다.
  • 쓰기 API가 규칙을 검증하지 않는 경우, 판단은 호출하는 쪽의 책임이다. 제공된 쓰기(기록용) API들은 요청을 그대로 저장하기만 했고, 정책 위반 여부(기한이 지났는지, 금액이 과도한지)를 전혀 걸러주지 않았습니다. 처음에는 당연히 API 쪽에서 막아줄 거라 생각했는데, 그렇지 않다는 걸 확인한 뒤로는 "에이전트가 API를 호출하기 전에 반드시 정책을 먼저 판단하고, API는 그 판단이 끝난 결과만 기록하는 용도로 쓴다"는 원칙으로 설계를 바꿨습니다. 시스템 경계가 어디까지 책임지는지를 확인하지 않으면 책임져야 할 판단을 시스템에 떠넘기게 된다는 걸 배웠습니다.
  • 되돌릴 수 없는 한도는 설계를 더 신중하게 만든다. 평가 단계의 API 호출 한도는 시간창 제한과 별개로 총 누적 한도가 있었고, 이 누적 한도는 초과하면 복구되지 않는 구조였습니다. 연습 단계에서는 자유롭게 호출을 반복해도 됐지만, 평가 단계로 넘어가면 "조회 한 번"도 아껴야 하는 자원이 됐습니다. 이런 비가역적 제약이 있는 자원은 평소 습관대로(일단 조회해보고 판단) 다루면 안 되고, 호출 전에 "이게 정말 필요한 조회인가"를 먼저 따지는 설계가 필요하다는 걸 배웠습니다.
  • 자유 문자열로 열려 있는 분류값은 직접 설계해야 한다. 담당자 이관(에스컬레이션) 기능의 "어디로 보낼지" 값이 미리 정해진 목록이 아니라 자유 문자열이었습니다. 시스템이 분류 체계를 대신 정해주지 않는다는 뜻이라, 인터뷰로 확인한 실제 담당자 구조를 바탕으로 이관 대상 이름 자체를 직접 설계해야 했습니다. API 명세를 읽을 때 "이 필드가 고정된 선택지인지, 호출하는 쪽이 의미를 채워야 하는 자유값인지"를 구분하는 습관이 생겼습니다.
  • 연동 작업은 체크리스트 하나를 빠뜨리면 그 전까지의 모든 설계가 무효가 된다. 채널 공개 설정, 식별값 혼동(비슷하게 생긴 두 개의 키 값을 구분하는 것), 테스트 계정 접근 가능 여부처럼 사소해 보이는 설정이 누락되면 그 앞의 모든 지식베이스·판단 로직 설계가 평가 자체를 받지 못하는 결과로 이어질 수 있었습니다. "로직을 잘 만드는 것"과 "그 로직이 실제로 평가받을 수 있는 상태로 배포하는 것"은 완전히 다른 종류의 꼼꼼함이 필요하다는 걸 체감했습니다.

6다시 그려본 구조 — 담당자 1명당 에이전트 1개, 그리고 손으로 먼저 그려본 흐름

담당자별로 실제 성과가 완전히 갈렸습니다. 어떤 담당자는 질문을 많이 던질수록 새로운 사실이 계속 나왔고, 어떤 담당자는 몇 번을 물어도 "확인이 필요하다"는 답만 돌아왔습니다. 이걸 한 사람(저)이 순서대로 돌면서 대응하다 보니, 반응이 잘 나오는 담당자에게 집중할지 반응이 느린 담당자를 더 캐물을지를 그때그때 감으로 정했습니다. 다시 한다면 이 판단 자체를 구조로 만들어야 한다고 생각합니다.
