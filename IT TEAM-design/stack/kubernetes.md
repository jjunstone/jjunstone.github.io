# Kubernetes 컨테이너 오케스트레이션 (클라우드-네이티브)

## 용도
- 마이크로서비스 배포 및 관리
- 자동 스케일링 (트래픽 변화 대응)
- 무중단 업데이트 (rolling update)
- 서비스 복원력 확보

## 이 기술 때문에 생기는 업무

### 정기 업무
- 일일: 클러스터 상태 모니터링, Pod 헬스 확인
- 주간: 성능 튜닝, 노드 최적화
- 월간: 보안 패치, 클러스터 업그레이드

### 요청 기반 업무
- 신규 애플리케이션 배포
- 스케일 조정 (CPU, 메모리)
- 네트워크 정책 변경

### 장애 업무
- Pod 재시작 또는 재배포
- 노드 장애 대응
- 리소스 부족 시 확장

## 연결되는 다른 기술
- CI/CD 파이프라인 (자동 배포)
- 클라우드 인프라 (Azure AKS)
- 모니터링 (Prometheus, Grafana)
- 서비스 메시 (Istio, 트래픽 제어)

## 담당과 승인 경계
- 담당: 인프라/DevOps과장, DevOps사원
- 승인: 인프라/DevOps과장 (배포 정책)
- 협력: 개발팀 (애플리케이션 배포)

## 관련 규제 조항
- ISO 27001 A.12.2: 변경 관리
- ISO 27001 A.14.1: 안전한 개발
- ISMS-P: 배포 통제 및 감시

## 10명으로 운영 가능한 이유 또는 한계

**가능한 이유:**
- Azure AKS (관리형): 마스터 노드 자동 관리
- 자동 스케일링: 수동 개입 최소화
- 자동화 배포: CI/CD로 배포 자동화

**한계:**
- 초기 설계 및 구축에 외부 전문가 필요
- 마이크로서비스 아키텍처 전환 필수
- 운영 복잡도: 전통 서버 관리보다 높음

## 대안 비교

### 옵션 A: 직접 관리형 Kubernetes (온프레미스)
**개요:** 자체 Kubernetes 클러스터 구축
**장점:** 완전 제어, 캐시인 메커니즘 불필요
**단점:** 운영 부담 매우 높음 (10명 팀에 부담)
**10명 운영 적합도:** 낮음
**규모감:** 고
**회수비용:** 낮음 (인프라 자산)
**다른 영역 영향:** 운영 비용 증가 (전문가 고용 필요)

### 옵션 B: Azure Kubernetes Service (AKS) (권장)
**개요:** 마이크로소프트 관리형 K8s
**장점:** 마스터 노드 자동 관리, Azure 통합, 자동 업데이트
**단점:** 클라우드 비용, 벤더 종속성
**10명 운영 적합도:** 높음 (관리 부담 최소)
**규모감:** 중
**규제 적합성:** 완전
**회수비용:** 높음 (클라우드 → 온프레미스 전환 어려움)
**다른 영역 영향:** 클라우드 비용 증가, 다른 인프라 투자 제약

### 옵션 C: Docker Swarm (전통 모놀리식)
**개요:** 간단한 컨테이너 오케스트레이션
**장점:** 배우기 쉬움, 관리 간단
**단점:** 고급 기능 부족, 스케일링 제한, 업계 퇴조 추세
**10명 운영 적합도:** 높음 (하지만 미래성 낮음)
**규모감:** 낮-중
**규정 준수:** 기본만 가능
**회수비용:** 중간 (Kubernetes로 마이그레이션 필요)
**다른 영역 영향:** 확장성 제약, 향후 전환 비용

## 권장안
**Azure Kubernetes Service (AKS)**

**근거:**
1. 운영 효율성: 마스터 노드 자동 관리로 팀 부담 최소화
2. 확장성: 마이크로서비스로 개발 속도 향상
3. 자동화: CI/CD 통합으로 배포 속도 향상
4. 규정 준수: 컨테이너 보안 및 감시 기능 우수
5. Azure 통합: PostgreSQL, Monitor 등과 원활한 연동

**초기 투자:** 높음 (설계, 마이그레이션)
**운영 효율:** 높음 (자동화 수준)
**장기 효과:** 개발/운영 민첩성 대폭 향상
